# Module Ownership

Companion to `docs.dbml` (canonical). Explains who owns which Postgres
schema, what a module is allowed to touch, and where the boundaries are.

Facts in this document are derived from `docs.dbml` and were checked by
parsing it (`@dbml/core` 11.0.0, transient, outside the repo).

## The rule

- Each **module** owns exactly one Postgres **schema**. The one historical
  two-schema exception (Inventory owning a separate `warehouse` schema) is
  **gone**: the physical estate now lives inside `inventory` as
  `inventory.warehouses`, `inventory.warehouse_addresses` and
  `inventory.warehouse_storages` (ADR-0008). The Identity module owns the
  single `auth` schema, shared by Better Auth's 9 core tables and the 6 ERP
  extension tables.
- A **foreign key may only connect two tables of the same module**.
  `docs.dbml` contains 226 `Ref:` declarations and **0 cross-module refs**
  (`validate-dbml.ts` now checks all 226; before 2026-11-05 it read
  `db.refs`, which `@dbml/core` v11 leaves empty, so the check passed vacuously).
- A **cross-module link** is a plain id column plus a column note that **starts
  with** the sentence below — `gen-logical-references.ts` anchors its regex at
  the start of the note, so a note that buries these words mid-sentence is
  silently not counted:
  `Logical reference to <target>.id. Cross-module FK intentionally omitted.
  Validated through the <Module> module contract.`
- 522 such logical reference columns exist (target count re-verified on each validation run, see validate-dbml.ts).
- Every one of them is a **nullable** plain id column (ADR-0014); presence is
  a service-layer fact, enforced by the owning module's contract method, not
  by the database.
  Full list in `logical-references.md`.
- Cross-module reads and writes go through the owning module's exported
  service contract. Another module's repository is never imported.

## Module profiles

### 1. Identity — `auth` (single schema)

- **Owns** the 9 Better Auth core tables (`users`, `sessions`, `accounts`,
  `verifications`, `organizations`, `members`, `invitations`, `passkeys`,
  `apikeys`) and the 6 ERP extension tables folded into the same schema
  (`user_profiles`, `user_role_assignments`, `portal_identities`,
  `user_preferences`, `identity_verifications`, `user_devices`).
- The fold keeps Better Auth's adapter contract intact: the 9 core tables are
  regenerated by Better Auth and are never hand-edited; the 6 extension
  tables are ERP-owned Drizzle tables that happen to live in the same Postgres
  schema. They keep their own `created_at`/`updated_at`/`deleted_at`.
- **Does not own** roles and permissions. The ERP role vocabulary is code
  (`packages/common/src/authorization/erp-permissions.ts`), not a table.
  `auth.members.role` carries the role key, `auth.user_role_assignments`
  carries extra scoped grants.
- **Contract**: `resolveOrganization(userId)`, `resolveUser(userId)`,
  `resolvePortalIdentity(portalType, entityId)`.

### 2. Location — `location`

- **Owns** the Indonesian administrative hierarchy: `provinces`, `regencies`,
  `districts`, `villages`. Global reference data, not tenant scoped.
- Seeded from `database/seeders/raw/location/*.json`, idempotently.
- **Contract**: `resolveLocation(villageId)` returning the full path.
- The four tables are the reason `location` is a module: 6 address columns
  in CRM, HR, Procurement, Organization and Investor point at them.

### 3. Company — `company`

- **Owns** the one legal company behind every organization (ADR-0011): the
  profile (`company.profiles`), head office addresses, contacts, bank
  accounts and company-wide settings. Every table is company-wide — no
  `organization_id` column anywhere in the schema.
- `company.profiles.document_code` feeds the `{COMPANY}` token of the
  numbering patterns (ERP-0009).
- **Contract**: `ExportedCompanyService.getProfile()` — the letterhead data
  other modules render.
- **Does not own** cash/bank operational balances (Finance owns
  `finance.cash_bank_accounts`) or anything organization-scoped.

### 4. Code Number — `code_number`

- **Owns** the one numbering authority (ERP-0009, moved from Organization in
  ERP-0042): one code series per code type for the whole company
  (`code_number.series`, was `organization.document_sequences`).
- The owning module calls `CodeNumberService.next(codeType)` inside its own
  transaction; allocation is one atomic
  `INSERT ... ON CONFLICT DO UPDATE ... RETURNING`.
- Generates document codes for every module and entity codes (employee,
  project, asset, warehouse); items keep their business SKU
  (ERP-0043 adds auto `code` per item kind).

### 5. Organization — `organization`

- **Owns** the internal structure of the company: branches, departments,
  positions, cost centres, fiscal settings and organization-scoped settings.
  Every table is tenant scoped by `organization_id`.
- The company profile, bank accounts and the numbering authority moved out to
  the Company and Code Number modules (ERP-0042).
- **Does not own** cash/bank operational balances (Finance owns
  `finance.cash_bank_accounts`).

### 6. CRM — `crm`

- **Owns** the customer master: customers, groups, contacts, addresses
  (one table with a `kind` discriminator), leads and lead activities,
  segments and segment members, interactions, credit limit history.
- `crm.customer_addresses` replaces a separate billing/shipping pair.
- **Contract**: `assertCustomerOwnedByOrganization(customerId, orgId)`,
  `resolveCustomerContact`, `resolveCustomerAddress`.

### 7. Catalog — `catalog`

- **Owns** the unified goods-and-service master: categories, units, items,
  variants, unit conversions, bundles, attributes, documents, price lists and
  prices, supplier offerings, cost history.
- One `catalog.items` table with an `item_type` discriminator
  (`good|service|bundle|subscription`) instead of parallel product/service
  tables.
- **Contract**: `resolveItem`, `resolvePrice(itemId, priceListId, date)`.

### 8. Sales — `sales`

- **Owns** quotations, quotation items, discount requests, sales orders,
  sales order items, contracts, sales targets, status histories, sales
  returns, delivery notes.
- `sales.quotations` is shown in its **target** shape in `docs.dbml`. The
  scaffold table created by migration `20261029044823_dear_living_lightning`
  has a different shape and is **replaced**, not altered, by step S3 of
  `implementation-phases.md`.
- `sales.payments` is a **transitional scaffold scheduled for removal**; it is
  grouped separately in `docs.dbml` and dropped in step S7. The single
  payment ledger of the ERP is `finance.payments`.
- **Contract**: `assertQuotationBelongsToOrganization`, `resolveOrder`.

### 9. Procurement — `procurement`

- **Owns** supplier master (with contacts and addresses), purchase requests,
  purchase orders, goods receipts, purchase returns.
- Supplier bills and their payment live in Finance, not here.

### 10. Inventory - `inventory`

- **Owns** one schema. `inventory.warehouses`,
  `inventory.warehouse_addresses`, `inventory.warehouse_storages`,
  `inventory.items`, the authoritative `inventory.stock_movements` ledger, the
  `inventory.stock_balances` projection and `inventory.serial_tracked_items`.
- **No longer owns borrowing.** `borrowings` / `borrowing_lines` /
  `borrowing_events` moved to the Assets module (ERP-0036 D5): a borrowed
  thing is a physical asset, not a stock item, and asset borrowing must not
  write the stock ledger (`stock_movements.item_id` is NOT NULL).
  `serial_tracked_items` therefore serves serialized products only;
  `current_borrowing_line_id` is a superseded column awaiting cleanup (D17).
- `inventory.items` is the **one item master for the whole ERP**;
  `catalog.items` is superseded (ADR-0008). The `product:*` permission name is
  retained even though the table is `items`. `item_kind` is
  `product|component|material` only (D9) — physical tools are assets.
- `organization_id` is **nullable on every inventory table**, and `NULL` means
  "global / company-wide", not "missing" — see obligation 2 below, which has an
  explicit scope carve-out for nullable-org modules.
- `inventory.stock_movements` is the source of truth and is append-only: one
  row per movement, never updated, no `deleted_at`; a reversal is a new row.
  `stock_balances` is a projection maintained only by the Inventory service,
  inside the same transaction as the movement (no triggers).
- **Contract**: `postMovement`, `reserveStock`, `releaseReservation`,
  `assertItemTracked`, plus the placement asserts Assets calls before writing
  an asset location: `assertStorageInWarehouse(storageId, warehouseId)` and
  `assertWarehouseReachableByOrg(warehouseId, organizationId | null)` — the
  latter **returns true for every warehouse until ERP-0031 adds
  `inventory.warehouse_organizations`** (ERP-0036 Stage 0, B1).

### 11. Projects — `projects`

- **Owns** project types, projects, phases, tasks and dependencies, daily
  reports, site assignments, KPI definitions and evaluations, milestones,
  change orders, handover, work plans.
- Zero intra-module foreign keys by design: every relation inside the module
  is a logical id on `projects.projects.id`, validated by the Projects
  service. This keeps the module easy to seed and to extend.

### 12. HR — `hr`

- **Owns** employee master, addresses, employment contracts, attendance and
  attendance corrections, leave types and requests, disciplinary records,
  training, certifications, salary components, bank accounts, emergency
  contacts, employee documents, transfers, separation records.
- Salary component **definitions** belong to Payroll; HR only holds the
  effective dated amount per employee.
- Employee bank details are restricted data; never exposed by an export that
  does not require the `employee` read permission.

### 13. Payroll — `payroll`

- **Owns** salary components, payroll periods, payroll runs, payslips and
  payslip items, payroll inputs, adjustments, payment batches and payment
  items, BPJS registrations, payslip acknowledgements.
- The payslip component lines are a **snapshot**, so a later component
  change never rewrites a historical payslip.

### 14. Finance — `finance`

- Sales owns invoices and invoice items (`sales.invoices`, plan D2); finance
  owns **the single payment ledger**
  (`finance.payments`), receipts, supplier bills, payment terms, expense
  claims, employee advances, expense settlements, cash and bank accounts,
  cash bank transactions, bank reconciliations, credit memos, payment
  allocations.
- One payment row can settle at most one invoice, one supplier bill and one
  employee advance. Nothing else in the ERP records a money movement.
- Advances and settlements have exactly one ledger: `finance.employee_advances`
  and `finance.expense_settlements`.

### 15. Accounting — `accounting`

- **Owns** the chart of accounts, journal entries and lines, accounting
  periods, tax types and tax records, opening balances, account balances,
  bank account links, withholding tax records, settings, journal templates.
- A journal entry is only postable when debit equals credit. The check is in
  the service (transactional) and mirrored by a database check constraint.

### 16. Assets — `assets`

- **Owns** asset types (global lookup), categories, the asset register, the
  physical movement history, maintenance, depreciation, disposal, documents,
  condition checks, tool sets and items, and the **borrowing engine**
  (`borrowings` / `borrowing_lines` / `borrowing_events`, moved from Inventory
  in ERP-0036 D5).
- **One row per physical unit** (D1): an asset is a serialized, borrowable
  object; quantity is always 1. Bulk consumables stay in `inventory.items`.
- **Location.** `assets.warehouse_id` / `storage_id` record the unit's current
  place, and `asset_movements` records every move with both location ids.
  They are **logical references into `inventory`** — no cross-schema FK.
  Placement is validated through the Inventory contract, never by joining
  inventory tables from this module.
- **Borrowing is the only custody mechanism** (D6): `asset_assignments` is
  dropped; internal lending is a borrowing with `purpose='internal_use'`.
  Borrowing writes `asset_movements` and never the stock ledger.
- **Tenancy.** `organization_id` is nullable (global = company-wide); global
  rows are app-admin write and org-read. Asset `code` is globally unique and
  allocated from the global numbering sequence (D13).
- Depreciation references `accounting.journal_entries.id` logically.
- **Contract**: the borrowing service is consumed in-process by the Asset
  controllers; other modules reference assets only by id
  (`resolveAsset(id, orgId)`).

### 17. After-Sales — `aftersales`

- **Owns** warranty policies and claims, service tickets, comments, work
  orders, parts usage, technician assignments, SLA policies, maintenance
  schedules, plans, visits and visit tasks, satisfaction surveys, spare
  parts, service contracts.
- Zero intra-module foreign keys by design; the After-Sales service
  validates its own hierarchy.

### 18. Document — `document`

- **Owns** document templates, the document registry (`document.documents`),
  files, signatures, access logs, shares, tags and tag links. Was schema
  `documents` with `documents.*` table names until ERP-0042.
- Registry + issuance: business documents stay in their owning module's
  tables; this module owns the issued copy, its files and signatures.
- `organization_id` is nullable: NULL means company-wide (ADR-0011 pattern
  of Inventory and Assets).
- File bytes live in object storage; this module owns metadata and access
  rules. A document is never hard deleted, a new version supersedes the old.

### 19. Approval — `approval`

- **Owns** approval policies, immutable policy versions, approval requests,
  stages, decisions, delegations, amount thresholds.
- The module owns the **decision record**, never the business document. The
  business module owns the document and calls the Approval contract.
- Policy versions are immutable: a change creates a new version, and an
  approval request always points at the version that was in force.

### 20. Budgeting — `budgeting`

- **Owns** budget periods, budgets and items, revisions and revision items,
  executions, cash flow plans and items.

### 21. Investor — `investor`

- **Owns** investor master and addresses, capital commitments and deposits,
  fund allocations, profit sharing schemes and entries, profit distribution
  runs and shares, investor reports, investor meetings.
- The profit distribution run is per period; `investor.profit_shares` is per
  investor. The cash movement is a `finance.payments` row.

### 22. Commerce — `commerce`

- **Owns** public web pages, menus and menu items, catalog publications and
  their items, promotions and rules, public shop orders and their items.
- A commerce order is **not** a sales order. The Sales module owns the
  confirmed order.

### 23. Automation — `automation`

- **Owns** integrations and encrypted credentials, workflows and steps,
  workflow and step runs, scheduled jobs and executions, the transactional
  outbox, notification templates and notifications.
- Secrets are only in `automation.integration_credentials.secret_value_encrypted`.
  No read endpoint returns the plain value.
- Long-running queues stay in the Redis worker. This module owns the
  schedule and the log, not the queue transport.

### 24. Licensing — `licensing`

- **Owns** licensable applications, packages, contracts, keys, activations,
  entitlements and usages, subscription schedules, license events.
- One integrated pilot application at the moment.

### 25. Ticketing — `ticket`

- **Owns** ticket categories, tickets, messages, attachments and the status
  history of the customer issue tickets (see 10b for the profile).

### 26. Audit — `audit`

- **Owns** one append-only trail: `audit.audit_logs`.
- `organization_id` is nullable because a global admin action can happen
  outside any organization.
- `actor_user_id` is a logical reference, so deleting a user never erases the
  trail.

## Why there is no `erp` schema

`architecture.md` and `data-model.md` still mention an `erp` schema with
`audit_logs`, `customers` and `investors`. **That schema does not exist** in
any migration. The only schemas in the database today are `auth`, `location`
and `sales` (see `database/migrations/`). `audit.audit_logs` replaces the
planned `erp.audit_logs`; `crm.customers` replaces the planned
`erp.customers`; `investor.investors` replaces the planned `erp.investors`.
See `implementation-phases.md` step S1.

## Cross-module contract obligations

Every logical reference implies a promise by the owning module:

1. **Existence** — the id resolves to a row of the target module.
2. **Tenant** — the row belongs to the same `organization_id` as the
   referring row. This is the rule that protects against cross-tenant
   leakage, and it is enforced in the owning module's read and assert
   methods, not by a foreign key.
   - **Nullable-org carve-out (ADR-0008; Assets since ERP-0036 D11).**
     Inventory and Assets rows may have a *null* `organization_id`, meaning
     global/company-wide, so "same `organization_id`" becomes "same scope": a
     global row is readable by every organization, an organization-scoped row
     only by its own. The obligation is *not* dropped for these modules — it is
     restated as `referrow.organization_id IS NULL OR
     referrow.organization_id = owner.organization_id`. Callers must never
     interpret `NULL` as "any organization".
3. **Lifecycle** — the target is soft deleted, not hard deleted, so a
   reference stays resolvable for history.
4. **Nullability** - every cross-module reference is nullable (ADR-0014), so
   the column itself never states whether the link is mandatory. That is a
   business fact: the referring module's service decides whether the link is
   required for the use case, and enforces it before the write.

The service layer must call the owning module's assert method before writing
a row that carries a logical reference. This is the replacement for the
integrity a foreign key would have given.
