# Data Dictionary

Companion to `docs.dbml` (canonical). The column conventions that apply to
every table, then the per-module glossary of business terms and status
vocabularies.

## 1. Column conventions

### 1.1 Primary key

| Rule | Value |
|---|---|
| Type | `uuid` |
| Default | `uuidv7()` (PostgreSQL 18 native) |
| Nullable | never |

```dbml
id uuid [pk, default: `uuidv7()`]
```

`uuidv7()` is time ordered, so the primary key sorts roughly by creation
time and index locality stays good. It is the PostgreSQL 18 built-in; the
database in `docker-compose.yml` is PostgreSQL 18.

**Exception — Better Auth tables.** The 9 tables in `auth` use `text` ids
generated by Better Auth (`id text [pk]`). They are not hand-managed and
must never be edited. Any column that references `auth.users.id` or
`auth.organizations.id` is therefore `text`, not `uuid`.

### 1.2 Tenant column

| Rule | Value |
|---|---|
| Name | `organization_id` |
| Type | `text` |
| Nullable | nullable on every table that carries it (ADR-0014) |
| Logical target | `auth.organizations.id` |

`organization_id` is a plain nullable logical reference to
`auth.organizations.id` on every table that carries it (ADR-0014). Presence
is a service-layer fact: the owning module's contract validates it before the
write, and the database does not enforce it. It is the first filter in every
query; for a nullable-org module the filter is `organization_id IS NULL OR
organization_id = $1`. A row without an organization is not visible to an
organization-scoped query, so an unlinked row reads as absent rather than as
another organization's data.

**Scope carve-out.** The modules that define an explicit global scope
(`inventory.*` since ADR-0008, `assets.*` since ERP-0036 D11) read `NULL` as
"company-wide", not "missing", and `audit.audit_logs` may record a global admin
action outside any organization. Everywhere else `NULL` means "not linked".

**Implementation status.** ADR-0014 is accepted; the column flip in
`docs.dbml` and its append-only migration are tracked as ERP-0037. Until that
lands, `organization_id` is still `NOT NULL` in the shipped schema.

**Scope note (ADR-0007).** These tenant-scoped ERP tables are part of the
target data model and are **not yet built** — the shipped schema has no
`organization_id` on master data, and master data is shared company-wide
across the company's organizations. The column becomes meaningful only if
ADR-0001's multi-tenancy migration path is ever executed.

`location.*` tables are global reference data and carry no
`organization_id`.

**App-scope tables carry no tenant column at all.** `notification.*` is
deliberately app-scope: a notification belongs to one user, is readable from
every organization that user belongs to, and the organization context travels
as a display tag (the organization name). Do not add `organization_id` there;
the list endpoint filters by `user_id` only.

### 1.3 Datetimes

Two different kinds, never mixed up.

| Kind | Type | Meaning | Column naming |
|---|---|---|---|
| **Operational timestamp** | `bigint` | Unix milliseconds since epoch, UTC. When the system event happened. | `created_at`, `updated_at`, `*_at`, `*_on` for operational dates |
| **Business date** | `date` | A calendar day in `Asia/Jakarta`. No time component. | `*_date`, `issue_date`, `due_date`, `start_date`, `end_date` |

```dbml
created_at bigint [not null]
updated_at bigint [not null]
delivery_date date
```

`bigint` unix milliseconds is the repository convention
(`apps/backend/drizzle/datatypes/unix-timestamp.ts`, skill
`drizzle-unix-timestamp`). It is used for every ERP table. The `auth.*`
tables keep the Better Auth native `timestamp` type and are not converted.

**Units warning.** Better Auth option timestamps are in **seconds**. Redis
cache TTLs are in **milliseconds**. ERP columns are **milliseconds**. Never
mix.

### 1.4 Money

| Rule | Value |
|---|---|
| Type | `bigint` |
| Unit | exact minor units (rupiah cents) |
| Currency | `currency_code varchar(3) NOT NULL DEFAULT 'IDR'` |
| Floats | forbidden (ADR-0002) |

```dbml
grand_total bigint [not null, default: 0]
currency_code varchar(3) [not null, default: 'IDR']
```

`bigint` holds up to Rp 92 quadrillion in minor units. `integer` (the
current `sales.payments.amount`) overflows at Rp 21.4 million, which is
the defect flagged in `module-ownership.md` and fixed in step S7.

Column naming for money:

| Suffix | Meaning |
|---|---|
| `_amount` | a single monetary amount |
| `_total` | a computed total of lines |
| `_cost` | a cost, not a price |
| `_price` | a unit price |
| `_value` | a book value or an allocated value |

### 1.5 Quantity

| Rule | Value |
|---|---|
| Type | `numeric(18,3)` |
| Reason | fractional units such as 1.5 m of cable, 0.25 hour of labour |

Quantity is not money and may be fractional, so `numeric` is correct here.
Percentages use `numeric(9,4)` and rates `numeric(18,6)`.

### 1.6 Codes

| Rule | Value |
|---|---|
| Name | `code` |
| Type | `varchar(32)` |
| Unique | per organization, `(organization_id, code)` |
| Reuse after soft delete | allowed, see the partial unique index `WHERE deleted_at IS NULL` in the Drizzle schemas |

Codes are the human reference of a document (`SPH-2026-0001`, `PO-2026-0007`)
and are allocated from `code_number.series`, never generated ad hoc.

**Nullable `organization_id` and codes.** A unique index ignores `NULL`, so
`(organization_id, code)` alone lets two rows without an organization share a
code. A table whose `organization_id` is nullable therefore uses the ADR-0008
pair: `(organization_id, code) WHERE organization_id IS NOT NULL` plus
`(code) WHERE organization_id IS NULL`.

**Exception — `assets.assets.code` is globally unique** (ERP-0036 D13), not
per organization: an org-scoped asset and a global asset must never share a
code, which `(organization_id, code)` cannot express because `NULL` never
conflicts in a unique index. Asset register codes therefore allocate from the
global (`''` sentinel) sequence regardless of tenant. Serial numbers are
unique per *scope* via `(coalesce(organization_id,''), serial_number)`.

### 1.7 Status columns

| Rule | Value |
|---|---|
| Type | `text` |
| Default | the initial status of the lifecycle |
| Guard | a `Checks { }` block listing every allowed value |

```dbml
status text [not null, default: 'draft']
Checks {
  `status IN ('draft', 'submitted', 'approved', 'rejected', 'cancelled')`
}
```

**No database enums.** A native `enum` type lives in `public` and would
break the schema isolation rule, and adding a value to a Postgres enum is a
`ALTER TYPE` that cannot run inside a transaction with other work. A `text`
column plus a `CHECK` gives the same guarantee with a plain `ALTER TABLE
... DROP CONSTRAINT / ADD CONSTRAINT`.

### 1.8 Soft delete

| Rule | Value |
|---|---|
| Column | `deleted_at bigint` |
| Nullable | yes |
| Meaning | Unix milliseconds of the deletion, `NULL` = row is live |

Rows are never hard deleted by feature code. Master data referenced by a
financial transaction cannot be hard deleted at all.

Tables carrying `deleted_at`: every business table of every module,
including the Identity link tables, the Ticketing module and the
`warehouse.*` structure tables. Tables **without** `deleted_at` are ledger,
log or projection tables: they are append-only (or derived) and are marked
with a status instead of a deletion timestamp
(`accounting.journal_entries`, `accounting.journal_lines`,
`inventory.stock_movements`, `inventory.stock_balances`,
`inventory.serial_tracked_items`, `inventory.lot_batches`,
`assets.borrowing_events`,
`sales.quotation_status_history`, `sales.order_status_history`,
`ticket.ticket_status_history`, `approval.approval_decisions`,
`approval.approval_policy_versions`, `automation.outbox_messages`,
`audit.audit_logs`, `document.access_logs`).

### 1.9 Audit columns

| Column | Type | Rule |
|---|---|---|
| `created_at` | `bigint` | `NOT NULL`, set by the service, unix ms |
| `updated_at` | `bigint` | `NOT NULL`, maintained by the service |

Some existing tables use `updated_at` nullable (the `location.*` tables,
reproduced from the live migration). New tables use `NOT NULL`.

### 1.10 Actor columns

| Suffix pattern | Type | Meaning |
|---|---|---|
| `created_by`, `requested_by`, `prepared_by`, `submitted_by`, `posted_by`, `executed_by`, `received_by`, `verified_by`, `approved_by`, `closed_by`, `reopened_by`, `reconciled_by`, `changed_by`, `checked_by`, `moved_by`, `handled_by`, `counted_by`, `calculated_by`, `issued_by`, `published_by`, `assigned_by`, `author_user_id` | `text` | the acting user, logical reference to `auth.users.id` |
| `*_user_id` (owner, manager, assignee, recipient, approver, signer) | `text` | the referenced user, logical reference to `auth.users.id` |
| `*_employee_id` | `uuid` | the referenced employee, logical reference to `hr.employees.id` |
| `*_by_employee_id` | `uuid` | the acting employee, logical reference to `hr.employees.id` |

Naming convention: `*_by` is always an **action** (someone did something),
`*_user_id` / `*_employee_id` is always a **role or reference** (someone is
attached to the record).

### 1.11 Boolean flags

| Pattern | Default | Meaning |
|---|---|---|
| `is_active` | `true` | the record is in use |
| `is_default` | `false` | the default of its kind |
| `is_primary` | `false` | the primary record of its kind |
| `is_stock_tracked` | `true` | the item has stock |
| `is_serialized` | `false` | the item is tracked per serial number |
| `is_locked` | `false` | the period cannot be edited |
| `is_current` | `true` | the current version of a document |
| `is_secret` | `false` | the setting value is a secret |
| `is_active` on a child table | `true` | see also `deleted_at` |

### 1.12 Free-form text

| Purpose | Type |
|---|---|
| codes, slugs, short labels | `varchar(32)` / `varchar(64)` / `varchar(128)` |
| names, descriptions, notes | `text` |
| structured but schema-less payloads (templates, config, criteria) | `text` holding JSON |
| structured payloads the ERP filters or searches inside | `jsonb` |

Structured payloads are stored as JSON text, not `jsonb`, because the shape
is owned by the calling module and the ERP does not query inside it.

**`jsonb` exception — notification payloads.** `notification.notifications`
uses `jsonb` for `tags`, `variables` and `metadata`, and
`notification.notification_templates` for `variables`, because those are
read as structured values by the API (tags are rendered as chips, variables
are interpolated by the client, metadata carries navigation targets). Never
store authorization facts in them: a `metadata` or `tags` value is display
data, and permission checks read the database columns, not the payload.

### 1.13 Index conventions

| Pattern | Index |
|---|---|
| business code | `(organization_id, code)` unique |
| foreign key column | single column index named `<table>_<column>_idx` |
| natural key | unique index named `<table>_..._uq` |
| scope-split unique (nullable org) | two partial uniques: `(organization_id, code) WHERE organization_id IS NOT NULL` and `(code) WHERE organization_id IS NULL` |
| scope-split unique where `NULL` never conflicts | expression index on `(coalesce(organization_id, ''), serial_number)` — a plain scope-split would let every global row repeat its natural key |
| globally unique despite a nullable org | a single unique index, no scope split (`assets.assets.code`)

Index names are `<table>_<column>_idx` or `<table>_<purpose>_uq`, so a name
in `docs.dbml` matches the name in the migration.

### 1.14 Null policy

| Rule | Reason |
|---|---|
| Mandatory business attributes are `NOT NULL` | a row that exists is a complete statement |
| Optional links are nullable | the link is optional in the flow |
| Mutable state columns carry `NOT NULL DEFAULT` | an implicit default hides bugs |
| `deleted_at`, `updated_at` are nullable | `NULL` has a meaning |

## 2. Generic column names

| Column | Type | Meaning in every module |
|---|---|---|
| `id` | `uuid` | primary key |
| `organization_id` | `text` | owning tenant |
| `code` | `varchar(32)` | human reference of the record |
| `name` | `text` | display name |
| `description`, `notes`, `remarks` | `text` | free-form explanation |
| `status` | `text` | lifecycle state, guarded by a `CHECK` |
| `type` | `text` | kind discriminator, guarded by a `CHECK` |
| `kind` | `text` | subtype discriminator, used where one table serves several purposes |
| `source_type` / `source_id` | `text` | polymorphic origin of a record |
| `reference_type` / `reference_id` | `text` | polymorphic target of a record |
| `document_id` | `uuid` | attached document |
| `warehouse_id` / `storage_id` | `uuid` | physical place: warehouse, and the storage (bin) inside it. Logical references to `inventory.warehouses` / `inventory.warehouse_storages`; a `storage_id` always implies its `warehouse_id` |
| `is_active` | `boolean` | in use |
| `created_at` / `updated_at` | `bigint` | audit timestamps |
| `deleted_at` | `bigint` | soft delete marker |

`source_type` / `source_id` pairs are the escape hatch for a link whose
target table varies (`inventory.stock_reservations` can hold stock for a
sales order, a project or a work order). They are always resolved through
the owning module's contract.

## 3. Status vocabularies

The complete list per column lives in the `Checks { }` block of each table
in `docs.dbml`. The lifecycles below are the recurring patterns.

### 3.1 Draft → submitted → approved / rejected

The generic approval flow, used by quotations, purchase requests, purchase
orders, stock adjustments, stock transfers, leave requests, attendance
corrections, disciplinary records, employee transfers, separation records,
expense claims, employee advances, invoice issues, budget revisions, capital
commitments, fund allocations, asset disposals, project changes, work plans.

```text
draft → submitted → approved → (executed | posted | paid | ...)
                 ↘ rejected
```

### 3.2 Requested → approved → executed

Used by `finance.payments`, `payroll.payroll_payments`, `sales.sales_returns`,
`procurement.purchase_returns`, `inventory.stock_adjustments`,
`aftersales.warranty_claims`, `investor.capital_deposits`.

```text
draft → submitted → approved → executed
```

`procurement.purchase_returns` names its executed state `shipped` (ERP-0061):
`draft → submitted → approved → shipped`, rejection back to `draft`,
`cancelled` before shipping.
`sales.sales_returns` names it `received` (ERP-0062): `draft -> submitted ->
approved -> received`, rejection back to `draft`, `cancelled` before
receiving.

### 3.3 Open → closed

Used by `aftersales.service_tickets`, `accounting.accounting_periods`,
`payroll.payroll_periods`, `budgeting.budget_periods`, `projects.projects`,
`licensing.license_contracts`.

### 3.4 Posted / reversed

Used by the ledger tables: `accounting.journal_entries`,
`inventory.stock_movements`, `finance.cash_bank_transactions`.

```text
draft → posted → reversed
```

A posted ledger row is never edited. A correction is a compensating row.

### 3.5 Draft → published → archived

Used by the content tables: `commerce.web_pages`, `document.documents`,
`investor.investor_reports`, `notification.notification_templates`.

### Assets

| Term | Meaning |
|---|---|
| asset | a tracked piece of equipment, a vehicle, a tool, IT hardware. **One row per physical unit** (ERP-0036 D1): quantity is always 1. |
| asset type | the global lookup row (`assets.asset_types`) that classifies an asset or category; `code` is the stable identity, `name` the editable label. |

| depreciation | the monthly book value reduction, with an audit trail. |
| disposal | the sale, scrap, donation or transfer of an asset. |
| condition check | a periodic inspection. |
| tool set | a kit lent to a technician as one unit; lending expands to one borrowing line per member asset. |

Asset status is **derived**, not hand-written, for unit-backed rows:
`ready | borrowed | maintenance | inactive | disposed | lost`. `inactive` is
the only asset-owned state (`deactivation_reason IS NOT NULL`) and survives a
reconcile.

## 6. Checks in the schema

Every status, type, kind and amount column that has a closed vocabulary
carries a `CHECK` constraint in `docs.dbml`. The categories:

| Category | Example |
|---|---|
| Status vocabulary | `status IN ('draft', 'submitted', 'approved')` |
| Type vocabulary | `item_type IN ('good', 'service', 'bundle', 'subscription')` |
| Non negative amount | `grand_total >= 0` |
| Strictly positive amount | `amount > 0` |
| Range | `progress_percent BETWEEN 0 AND 100` |
| Percentage | `share_percent >= 0 AND share_percent <= 100` |
| Date ordering | `end_date IS NULL OR end_date >= start_date` |
| Exclusive parent | `from_warehouse_id <> to_warehouse_id` |
| Exactly one parent | `(quotation_id IS NOT NULL AND sales_order_id IS NULL) OR (quotation_id IS NULL AND sales_order_id IS NOT NULL)` |
| Balanced entry | `total_debit = total_credit` |
| One sided line | `(debit > 0 AND credit = 0) OR (credit > 0 AND debit = 0)` |
| Transfer needs a target | `(movement_type IN ('transfer_in', 'transfer_out') AND target_warehouse_id IS NOT NULL) OR (movement_type NOT IN ('transfer_in', 'transfer_out'))` |
| Derived equality | `closing_balance = opening_balance + inflow_total - outflow_total` |
| Derived net | `net_amount = gross_amount - tax_amount` |
| Bounded subset | `settled_amount <= amount` |

The `CHECK` blocks are the second line of defence. The service layer is the
first line, because it can produce a readable error message; the constraint
is what actually stops a bad row.
