# Data Dictionary

Companion to `docs.dbml` (canonical). The column conventions that apply to
every table, then the per-module glossary of business terms and status
vocabularies.

## 1. Column conventions

### 1.1 Primary key

| Rule | Value |
|---|---|
| Type | `uuid` |
| Default | `uuidv7()` (PostgreSQL 18 native) |
| Nullable | never |

```dbml
id uuid [pk, default: `uuidv7()`]
```

`uuidv7()` is time ordered, so the primary key sorts roughly by creation
time and index locality stays good. It is the PostgreSQL 18 built-in; the
database in `docker-compose.yml` is PostgreSQL 18.

**Exception — Better Auth tables.** The 9 Better Auth core tables in `auth`
(`users`, `sessions`, `accounts`, `verifications`, `organizations`, `members`,
`invitations`, `passkeys`, `apikeys`) use `text` ids generated by Better Auth
(`id text [pk]`). They are not hand-managed. The two ERP extension tables in
the same schema (`user_invitations`, `organization_settings`) follow the
Better Auth id style too. Any column that references `auth.users.id` or
`auth.organizations.id` is therefore `text`, not `uuid`.

The baseline v2 contract (ADR-0024) is 18 Postgres schemas and 188 tables in
`docs.dbml`. Some tables are marked `status: target` in their note: they are
listed by the owning module but not built yet, so the generated baseline
migration creates fewer tables than `docs.dbml` lists.

### 1.2 Tenant column

| Rule | Value |
|---|---|
| Name | `organization_id` |
| Type | `text` |
| Nullable | nullable on every table that carries it (ADR-0014) |
| Logical target | `auth.organizations.id` |

`organization_id` is a plain nullable logical reference to
`auth.organizations.id` on every ERP table that carries it (ADR-0014). Presence
is a service-layer fact: the owning module's contract validates it before the
write, and the database does not enforce it. For a nullable-org table the
filter is `organization_id IS NULL OR organization_id = $1` where the table
defines a global scope, and `organization_id = $1` elsewhere. A row without an
organization is not visible to an organization-scoped query, so an unlinked
row reads as absent rather than as another organization's data.

**Exceptions inside `auth`.** `auth.members`, `auth.invitations` and
`auth.organization_settings` carry `organization_id text NOT NULL` with a real
intra-schema foreign key to `auth.organizations.id`
(`ON DELETE CASCADE`). `auth.user_invitations.organization_id` is nullable.

**Most business data is company-wide (ADR-0007, ADR-0011).** The company is
deployed once; organizations are internal departments, not tenancy
boundaries. Most business tables therefore carry **no** `organization_id` at
all: all of `company`, `customer`, `supplier`, `location`, `notification`,
`human_resource` (except `employees`), `procurement` (except
`purchase_requests`), `ticket` (except `ticket_templates`), and most of
`sale` (quotations, orders, delivery notes, returns) and `project` (projects,
tasks, leads, licensing, warranties). The tables that do carry the column, and
the module settings tables in `sale`, `inventory`, `human_resource` etc. that
are keyed only by `(setting_group, setting_key)`, are listed in `docs.dbml`;
read the table, never assume.

**Scope carve-out.** Where the column exists it is nullable. `inventory.*`
(ADR-0008), `finance.*`, `tax.*`, `document.*`, `payment.*` and the
organization-scoped part of `sale` / `project` read `NULL` as
"company-wide / global scope" where the table note says so ("Null means
global/company-wide"). `audit.audit_logs` may record a global admin action
outside any organization. Everywhere else `NULL` means "not linked".
There is no exception: `inventory.stock_adjustments.organization_id` is
nullable like the rest of `inventory.*` (it was `NOT NULL` in the Drizzle
schema until 2026-11-20, which contradicted ADR-0014). Its service still
writes the caller's active organization.

`location.*` tables are global reference data and carry no
`organization_id`.

**App-scope tables carry no tenant column at all.** `notification.*` is
deliberately app-scope: a notification belongs to one user, is readable from
every organization that user belongs to, and the organization context travels
as a display tag (the organization name). Do not add `organization_id` there;
the list endpoint filters by `user_id` only.

### 1.3 Datetimes

Two different kinds, never mixed up.

| Kind | Type | Meaning | Column naming |
|---|---|---|---|
| **Operational timestamp** | `bigint` | Unix milliseconds since epoch, UTC. When the system event happened. | `created_at`, `updated_at`, `*_at`, `*_on` for operational dates |
| **Business date** | `date` | A calendar day in `Asia/Jakarta`. No time component. | `*_date`, `issue_date`, `due_date`, `start_date`, `end_date` |

```dbml
created_at bigint [not null]
updated_at bigint [not null]
delivery_date date
```

`bigint` unix milliseconds is the repository convention
(`apps/backend/drizzle/datatypes/unix-timestamp.ts`, skill
`drizzle-unix-timestamp`). It is used for every ERP table. The Better Auth
core tables in `auth.*` keep the native `timestamp` type for their own
columns (`created_at`, `updated_at`, `expires_at` ...) and are not converted;
`deleted_at` on `auth.users` / `auth.organizations` is the `bigint` ERP
column.

**Units warning.** Better Auth option timestamps are in **seconds**. Redis
cache TTLs are in **milliseconds**. ERP columns are **milliseconds**. Never
mix.

### 1.4 Money

| Rule | Value |
|---|---|
| Type | `bigint` |
| Unit | exact minor units (rupiah cents) |
| Currency | `currency_code varchar(3) NOT NULL DEFAULT 'IDR'` |
| Floats | forbidden (ADR-0002) |

```dbml
grand_total bigint [not null, default: 0]
currency_code varchar(3) [not null, default: 'IDR']
```

`bigint` holds up to Rp 92 quadrillion in minor units. A 32-bit `integer`
overflows at Rp 21.4 million, which is why money is never `integer`; the
legacy `sales.payments` scaffold that had that defect is gone, and the single
payment ledger is `payment.payments.amount` (`bigint`).

Column naming for money:

| Suffix | Meaning |
|---|---|
| `_amount` | a single monetary amount |
| `_total` | a computed total of lines |
| `_cost` | a cost, not a price |
| `_price` | a unit price |
| `_value` | a book value or an allocated value |

### 1.5 Quantity

| Rule | Value |
|---|---|
| Type | `numeric(18,3)` |
| Reason | fractional units such as 1.5 m of cable, 0.25 hour of labour |

Quantity is not money and may be fractional, so `numeric` is correct here.
Percentages use `numeric(9,4)` (or `numeric(5,2)` for progress, weights and
hours); a few quantity-like values use `numeric(18,4)` (a line `quantity`, a
discount value, KPI target/actual) and coordinates use `numeric(10,7)`. Read
the column in `docs.dbml`.

### 1.6 Codes

| Rule | Value |
|---|---|
| Name | `code` |
| Type | `varchar(32)` |
| Unique | company-wide tables: `(code)`; organization-scoped tables: `(organization_id, code)` |
| Reuse after soft delete | allowed where the unique index is partial (`WHERE deleted_at IS NULL`); not every code index is, read the Drizzle schema |

Codes are the human reference of a document (`SPH-2026-0001`, `PO-2026-0007`)
and are allocated from the owning module's own `<schema>.code_numberings`
table through its `<Module>NumberingService` (ADR-0024 Q6, Q32), never
generated ad hoc. There is no central numbering schema: every business schema
(`customer`, `supplier`, `inventory`, `sale`, `procurement`, `finance`, `tax`,
`payment`, `project`, `ticket`, `human_resource`, `document`) owns one.
A `code_numberings` row is `(code_type, pattern, reset_policy, period_key,
next_number)`, unique on `code_type` for live rows, and allocation is one
atomic `INSERT ... ON CONFLICT DO UPDATE ... RETURNING`. The `{COMPANY}` token
comes from `company.profiles.document_code`.

**Nullable `organization_id` and codes.** A unique index ignores `NULL`, so
`(organization_id, code)` alone lets two rows without an organization share a
code. A table whose `organization_id` is nullable and that supports a global
scope therefore uses the ADR-0008 pair:
`(organization_id, code) WHERE organization_id IS NOT NULL` plus
`(code) WHERE organization_id IS NULL` (for example `inventory.products`,
`inventory.movements`, `inventory.borrowings`).

**Exception — `inventory.items.code` is globally unique** (`items_code_uq`,
live rows only), not per organization: an org-scoped physical unit and a
global one must never share a code, which `(organization_id, code)` cannot
express because `NULL` never conflicts in a unique index. (This was
`assets.assets.code` before `assets` was absorbed into `inventory`.) Serial
numbers of units are unique per *scope* via
`(coalesce(organization_id,''), serial_number)`.

### 1.7 Status columns

| Rule | Value |
|---|---|
| Type | `text` |
| Default | the initial status of the lifecycle |
| Guard | a `Checks { }` block listing every allowed value |

```dbml
status text [not null, default: 'draft']
Checks {
  `status IN ('draft', 'submitted', 'approved', 'rejected', 'cancelled')`
}
```

**No database enums.** A native `enum` type lives in `public` and would
break the schema isolation rule, and adding a value to a Postgres enum is a
`ALTER TYPE` that cannot run inside a transaction with other work. A `text`
column plus a `CHECK` gives the same guarantee with a plain `ALTER TABLE
... DROP CONSTRAINT / ADD CONSTRAINT`.

### 1.8 Soft delete

| Rule | Value |
|---|---|
| Column | `deleted_at bigint` |
| Nullable | yes |
| Meaning | Unix milliseconds of the deletion, `NULL` = row is live |

Rows are never hard deleted by feature code. Master data referenced by a
financial transaction cannot be hard deleted at all.

Tables carrying `deleted_at`: every business table of every module,
including the `inventory.warehouse_*` structure tables, the `ticket` tables
and `document.access_logs`. Tables **without** `deleted_at` are:

- **Ledger, log or projection tables**, append-only or derived, corrected by a
  compensating row or rebuilt, never deleted: `inventory.movements` (the stock
  ledger), `inventory.stocks` (the balance projection),
  `inventory.borrowing_events`, `inventory.borrowing_request_events`,
  `finance.ar_open_items`, `finance.ap_open_items` (open-item projections) and
  `audit.audit_logs`. (`finance.journal_entries` and `journal_lines` carry
  `deleted_at` and use a `status` of `posted` / `reversed` / `void` for the
  accounting lifecycle.)
- **Better Auth core tables** other than `auth.users` and
  `auth.organizations`: `auth.sessions`, `auth.accounts`,
  `auth.verifications`, `auth.members`, `auth.invitations`, `auth.passkeys`,
  `auth.apikeys`. Better Auth hard deletes them itself; they must never gain a
  `deleted_at` column nor be queried with one.

Pre-refactor history: `approval.approval_decisions`,
`approval.approval_policy_versions`, `ticket.ticket_status_history`,
`inventory.serial_tracked_items` and `inventory.lot_batches` used to be in
this list; those tables no longer exist (ADR-0024). The surviving
`sale.quotation_status_history` and `sale.order_status_history` carry
`deleted_at`, and `automation.outbox_messages` does too.

### 1.9 Audit columns

| Column | Type | Rule |
|---|---|---|
| `created_at` | `bigint` | `NOT NULL`, set by the service, unix ms |
| `updated_at` | `bigint` | `NOT NULL`, maintained by the service |

Some tables use `updated_at` nullable (for example `location.*`). Read the
column in `docs.dbml`.

### 1.10 Actor columns

| Suffix pattern | Type | Meaning |
|---|---|---|
| `created_by`, `requested_by`, `prepared_by`, `submitted_by`, `posted_by`, `executed_by`, `received_by`, `verified_by`, `approved_by`, `closed_by`, `reopened_by`, `reconciled_by`, `changed_by`, `checked_by`, `moved_by`, `handled_by`, `counted_by`, `calculated_by`, `issued_by`, `published_by`, `assigned_by`, `author_user_id` | `text` | the acting user, logical reference to `auth.users.id` |
| `*_user_id` (owner, manager, assignee, recipient, approver, signer) | `text` | the referenced user, logical reference to `auth.users.id` |
| `*_employee_id` | `uuid` | the referenced employee, logical reference to `human_resource.employees.id` |
| `*_by_employee_id` | `uuid` | the acting employee, logical reference to `human_resource.employees.id` |

Naming convention: `*_by` is always an **action** (someone did something),
`*_user_id` / `*_employee_id` is always a **role or reference** (someone is
attached to the record).

### 1.11 Boolean flags

| Pattern | Default | Meaning |
|---|---|---|
| `is_active` | `true` | the record is in use |
| `is_default` | `false` | the default of its kind |
| `is_primary` | `false` | the primary record of its kind |
| `is_stock_tracked` | `true` | the item has stock |
| `is_serialized` | `false` | the item is tracked per serial number |
| `is_current` | `true` | the current version of a document |
| `is_secret` | `false` | the setting value is a secret |

The set above is the recurring pattern, not a per-table list: `is_stock_tracked`,
`is_serialized` and `is_current` each occur on a single table, and there is no
`is_locked` column any more (a closed period is `finance.accounting_periods.status
IN ('closed', 'locked')`). Check the table in `docs.dbml` before relying on a
flag.
| `is_active` on a child table | `true` | see also `deleted_at` |

### 1.12 Free-form text

| Purpose | Type |
|---|---|
| codes, slugs, short labels | `varchar(32)` / `varchar(64)` / `varchar(128)` |
| names, descriptions, notes | `text` |
| structured payloads, snapshots and lists read as structured values by the API | `jsonb` |
| structured but schema-less payloads the ERP never reads inside | `text` holding JSON (rare; prefer `jsonb`) |

`jsonb` is the baseline v2 choice for structured payloads. Examples in
`docs.dbml`: customer/supplier snapshots frozen on quotations, orders,
invoices and purchase orders (`customer_snapshot`, `supplier_snapshot`),
`payment_schedule`, `serial_numbers` on delivery/receipt lines, handover and
warranty `items`, `payment.gateways.config`, `payment.payments.last_event`,
`automation.outbox_messages.payload` and `audit.audit_logs.meta`.

**Notification payloads.** `notification.push_notifications` uses `jsonb` for
`tags`, `variables` and `metadata`, and
`notification.push_notification_templates` for `variables`, because those are
read as structured values by the API (tags are rendered as chips, variables
are interpolated by the client, metadata carries navigation targets). Never
store authorization facts in them: a `metadata` or `tags` value is display
data, and permission checks read the database columns, not the payload.

### 1.13 Index conventions

| Pattern | Index |
|---|---|
| business code | company-wide tables `(code)` unique; org-scoped tables `(organization_id, code)` unique; partial `WHERE deleted_at IS NULL` where soft-deleted codes must be reusable |
| foreign key column | single column index named `<table>_<column>_idx` |
| natural key | unique index named `<table>_..._uq` |
| scope-split unique (nullable org) | two partial uniques: `(organization_id, code) WHERE organization_id IS NOT NULL` and `(code) WHERE organization_id IS NULL` |
| scope-split unique where `NULL` never conflicts | expression index on `(coalesce(organization_id, ''), serial_number)` — a plain scope-split would let every global row repeat its natural key |
| globally unique despite a nullable org | a single unique index, no scope split (`inventory.items.code`) |
| per-module numbering | `<schema>.code_numberings` unique on `code_type` (live rows) |

Index names are `<table>_<column>_idx` or `<table>_<purpose>_uq`, so a name
in `docs.dbml` matches the name in the migration.

### 1.14 Null policy

| Rule | Reason |
|---|---|
| Mandatory business attributes are `NOT NULL` | a row that exists is a complete statement |
| Optional links are nullable | the link is optional in the flow |
| Mutable state columns carry `NOT NULL DEFAULT` | an implicit default hides bugs |
| `deleted_at` is nullable; `updated_at` is `NOT NULL` where `docs.dbml` says so | `NULL` of `deleted_at` means "live"; `updated_at` is set by the service on every write |

## 2. Generic column names

| Column | Type | Meaning in every module |
|---|---|---|
| `id` | `uuid` | primary key |
| `organization_id` | `text` | owning organization scope, nullable logical reference; absent on company-wide tables (see 1.2) |
| `code` | `varchar(32)` | human reference of the record |
| `name` | `text` | display name |
| `description`, `notes`, `remarks` | `text` | free-form explanation |
| `status` | `text` | lifecycle state, guarded by a `CHECK` |
| `type` | `text` | kind discriminator, guarded by a `CHECK` |
| `kind` | `text` | subtype discriminator, used where one table serves several purposes |
| `source_type` / `source_id` | `text` | polymorphic origin of a record |
| `reference_type` / `reference_id` | `text` | polymorphic target of a record |
| `document_id` | `uuid` | attached document |
| `warehouse_id` / `storage_id` (`bin_id` on stock, movement and document-line tables) | `uuid` | physical place: warehouse, and the storage (bin) inside it. Intra-module foreign keys inside `inventory` (`inventory.warehouses` / `inventory.warehouse_storages`), logical references from other modules; a storage always implies its warehouse |
| `is_active` | `boolean` | in use |
| `created_at` / `updated_at` | `bigint` | audit timestamps |
| `deleted_at` | `bigint` | soft delete marker |

`source_type` / `reference_type` + id pairs are the escape hatch for a link
whose target table varies (`inventory.movements.reference_type` names the
document that caused a movement: goods receipt, delivery note, sale return,
purchase return, stock adjustment, borrowing, ...; `payment.payment_allocations`
carries `payable_type` + `payable_id`). They are always resolved through the
owning module's contract.

## 3. Status vocabularies

The complete list per column lives in the `Checks { }` block of each table
in `docs.dbml`. The lifecycles below are the recurring patterns. Tables whose
note starts with `status: target` are not built yet; their vocabularies are the
intended contract.

### 3.1 Draft → submitted → approved / rejected

The generic approval flow. There is no central `approval` module any more
(ADR-0024): each module owns its own status column and transition rules. Used
by `sale.quotations` (plus `sent | superseded | won | lost`),
`procurement.purchase_requests`, `procurement.purchase_orders`,
`procurement.purchase_returns`, `sale.returns`, `inventory.stock_adjustments`,
`inventory.disposals`, `finance.expense_claims`, `finance.employee_advances`,
`finance.expense_settlements`, `finance.journal_entries`,
`project.changes`, `project.work_plans`, `document.documents`,
`human_resource.leave_requests` and `human_resource.overtime_requests`
(the last two start at `submitted`).

```text
draft → submitted → approved → (executed | posted | paid | ...)
                 ↘ rejected
```

### 3.2 Requested → approved → executed

Used by `payment.payments`, whose vocabulary covers both manual and gateway
channels (`draft`, `submitted`, `approved`, `executed`, plus the gateway
states `pending`, `paid`, `expired`, `failed`, and `reversed`, `void`,
`cancelled`).

```text
draft → submitted → approved → executed
```

The executed state is named per document:
`procurement.purchase_returns` → `shipped`
(`draft → submitted → approved → shipped`, `cancelled` before shipping);
`sale.returns` → `received`
(`draft → submitted → approved → received`, `cancelled` before receiving);
`inventory.stock_adjustments` → `posted` (only `posted` writes movements);
`inventory.disposals` → `executed`; `finance.employee_advances` →
`disbursed` then `settled`.

### 3.3 Open → closed

Used by `finance.accounting_periods` (`open → closed → locked`),
`project.projects` (`active → closed`, `cancelled`), `sale.targets`,
`project.work_plans`, `ticket.tickets` (`new → in_progress → resolved →
closed`) and `human_resource.employee_tasks` (`open → done`).

### 3.4 Posted / reversed

Used by the ledger tables: `finance.journal_entries`,
`inventory.movements`, `finance.cash_bank_transactions`.

```text
draft → posted → reversed
```

A posted ledger row is never edited. A correction is a compensating row.

### 3.5 Draft → published → archived

Used by content-like tables. `document.documents` runs `draft → submitted →
approved → issued`, with `void`, `expired` and `archived` as terminal states.
`notification.push_notification_templates` has no status. The old
`commerce.web_pages` and `investor.investor_reports` no longer exist; the
public website listing now lives on `inventory.products` / `product_categories`.

## 4. Per-module glossary

Eighteen schemas (ADR-0024). Tables whose dbml note starts with `status: target` are listed by the owner but not built yet. Modules that were absorbed or removed are listed
at the end under "Removed pre-refactor terms".

### Identity (`auth`)

| Term | Meaning |
|---|---|
| organization | an internal organization of the company (e.g. HQ, a branch office). Multiple may exist inside the one company; each has its own membership (ADR-0001, ADR-0007). Not a tenancy boundary: ERP master data is shared company-wide. |
| member | a user inside an organization, with a role key (`auth.members.role`, comma-joined role keys). |
| role | the access-control key from `packages/common/src/authorization/erp-permissions.ts`. Not a table. |
| user invitation | an ERP-owned invitation (`auth.user_invitations`), distinct from the Better Auth organization invitation. |
| organization settings | per-organization key/value settings (`auth.organization_settings`). |
| portal login | not an identity table any more: the portal identity is folded into `customer.customers` (ADR-0024 Q5, Q12, Q16). |

### Location (`location`)

| Term | Meaning |
|---|---|
| province / regency / district / village | the Indonesian administrative hierarchy: provinsi, kabupaten/kota, kecamatan, kelurahan. |
| global reference data | shared by the whole company and by every organization; no `organization_id`. |
| village-level address | other modules store only `village_id`; the rest of the path is derived (ADR-0024 Q10). |

### Company (`company`)

| Term | Meaning |
|---|---|
| company profile | the legal identity of the company (`company.profiles`). The company is deployed once; it is not per organization. |
| document code | `company.profiles.document_code`, feeds the `{COMPANY}` numbering token. |
| onboarding image | the picture shown on the login page (`company.profiles.onboarding_object_key`), stored in object storage as WebP like the other profile images. |
| address / contact | the company address and contact rows (`company.addresses`, `company.contacts`). |
| settings | company-wide key/value settings (`company.settings`); organization-scoped settings live in `auth.organization_settings`. |

Branches, departments, positions and cost centres are **not** in `company`:
the standalone `organization` schema was removed (ADR-0024 Q4).

### Customer (`customer`, was `crm`)

| Term | Meaning |
|---|---|
| customer company | the B2B entity (`customer.companies`). |
| customer | the person: a contact of a company or an individual (`customer.customers`), including the portal login. |
| address | the customer or company address (`customer.addresses`, `customer.company_addresses`). |

Leads moved to `project`. Contacts merged into `customers`. Customer groups,
segments, interactions and credit limits no longer exist as tables.

### Supplier (`supplier`)

| Term | Meaning |
|---|---|
| supplier company | the entity a purchase order is issued to (`supplier.companies`). |
| supplier | the person / PIC (`supplier.suppliers`). Bank details are restricted. |
| address | `supplier.addresses`, `supplier.company_addresses`. |

### Inventory (`inventory`, absorbs `assets` and `catalog`)

| Term | Meaning |
|---|---|
| product | the SKU master (`inventory.products`), `product_kind` = product, component or material. Services are neither stocked nor serialized. The website listing columns are part of the product row (`is_published`, `slug`). |
| product category | one-level category, company-wide (`inventory.product_categories`). |
| item serial | a serialized **product** unit tracked by serial number (`inventory.item_serials`). |
| item | one physical unit (tool, vehicle, equipment) with its own status (`inventory.items`); quantity is always 1. A physical tool is an item, not a product. |
| movement | the authoritative append-only ledger of every quantity change (`inventory.movements`, was `stock_movements`). |
| stock | the balance projection derived from the movements (`inventory.stocks`, was `stock_balances`). |
| stock adjustment | a counted or justified correction with an approval chain; only `posted` writes movements. |
| borrowing request / borrowing | the custody mechanism for items: a request with an approval chain, then a borrowing issued against specific items, returned with a condition. |
| maintenance / condition check / disposal | the lifecycle of an item (`inventory.maintenances`, `condition_checks`, `disposals`). |
| tool set | a kit lent as one unit; lending expands to one borrowing line per member item. |
| warehouse / address / storage | the physical estate: `inventory.warehouses`, `warehouse_addresses` (1:1), `warehouse_storages` (one level deep, bins). |
| warehouse manager | the person-in-charge of a warehouse (ADR-0017), `inventory.warehouse_managers`. |
| warehouse organization | grants an organization access to a warehouse (ADR-0010). |

The separate `warehouse` schema in the original plan was retired (ADR-0008);
the physical structure lives in `inventory`. Item status is derived for
unit-backed rows: `ready | borrowed | maintenance | inactive | disposed |
lost`.

### Sale (`sale`, was `sales`)

| Term | Meaning |
|---|---|
| quotation (SPH) | the price proposal sent to a customer; `draft → submitted → approved → sent`, then `won`, `lost` or `superseded`. |
| order | the confirmed customer order (`sale.orders`). |
| delivery note (surat jalan) | the physical handover document. |
| return | goods returned by a customer (`sale.returns`). |
| invoice (faktur) | the customer receivable document, with an optional payment schedule. |
| receipt (kwitansi) | the customer-facing proof of a payment. Not a money movement. |
| discount request | a request to exceed the standard discount. `status: target`. |
| contract | the legal frame of the order and of the project. `status: target`. |
| target | the monthly or yearly target of a salesperson. `status: target`. |

### Procurement (`procurement`)

| Term | Meaning |
|---|---|
| purchase request (PR) | the internal request and approval gate before a purchase order exists. |
| purchase order (PO) | the order sent to a supplier. |
| goods receipt (GR) | the record of what was physically received against a PO; its only status is `posted`. |
| purchase return | goods sent back to a supplier. |

The supplier master is in `supplier`, not here.

## 6. Checks in the schema

Every status, type, kind and amount column that has a closed vocabulary
carries a `CHECK` constraint in `docs.dbml`. The categories:

| Category | Example |
|---|---|
| Status vocabulary | `status IN ('draft', 'submitted', 'approved')` |
| Type vocabulary | `product_kind IN ('product', 'component', 'material')` |
| Non negative amount | `grand_total >= 0` |
| Strictly positive amount | `amount > 0` |
| Range | `progress_percent BETWEEN 0 AND 100` |
| Percentage | `discount_percent IS NULL OR (discount_percent >= 0 AND discount_percent <= 100)` |
| Date ordering | `end_date IS NULL OR start_date IS NULL OR end_date >= start_date` |
| Same-record parent | `storage_id IS NULL OR warehouse_id IS NOT NULL` |
| No self reference | `task_id <> depends_on_task_id` |
| Balanced entry | `total_debit = total_credit` |
| One sided line | `(debit > 0 AND credit = 0) OR (credit > 0 AND debit = 0)` |
| Transfer needs a target | `(movement_type IN ('transfer_in', 'transfer_out') AND target_warehouse_id IS NOT NULL) OR (movement_type NOT IN ('transfer_in', 'transfer_out'))` |
| Bounded subset | `settled_amount <= amount` |

The `CHECK` blocks are the second line of defence. The service layer is the
first line, because it can produce a readable error message; the constraint
is what actually stops a bad row.
